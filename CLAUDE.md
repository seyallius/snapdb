# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`snapdb` (`github.com/seyallius/snapdb`) is a Go library for integration-test databases. It boots a DB once per test package (from `TestMain`), snapshots it in a known-good state, and restores the snapshot before every test via `snapdb.Reset`. It stays ORM-agnostic: callers supply callbacks and an `Engine` adapter. Long-form docs live as plain markdown in `docs/content/` (readable directly on GitHub) and are also published as a generated site at `docs/`; `docs/content/design-notes.md` explains the reasoning behind most API decisions.

## Commands

```bash
go test ./...                                   # unit tests (no Docker needed)
go test ./snapdb_test -run TestLifecycle_SlowPath -v   # single test
TEST_INTEGRATION=1 go test ./drivers/...        # MySQL/Postgres driver tests (need Docker)
go vet ./... && golangci-lint run && staticcheck ./...   # or: just all-checks
```

The `Justfile` wraps these (`just test`, `just lint`, `just bench`, …). One target points at a path that doesn't exist: `build-doppelgen` (`./cmd/doppelgen`).

## Documentation site

`docs/` is a static site generated by [benchbook](https://github.com/seyallius/benchbook) (`benchbook.toml` at the repo root), published via GitHub Pages. It serves two unrelated purposes bundled into one tool:

- **The real docs** — `docs/content/*.md` (home, quickstart, configuration, drivers, engine-and-environment, caching, design-notes) are hand-authored and listed in `benchbook.toml`'s `[[nav]]`. Edit these directly; they're never touched by a rebuild.
- **A microbenchmark history** — `snapdb_test/benchmark_test.go` holds `BenchmarkApplyOptions`, the only benchmark in the repo, which exists solely so benchbook has something real to track. Performance is not the point of this site.

Regenerate with `just docs` (`benchbook build`) after editing a content page, or `just docs-run` (`benchbook run`) after changing the benchmark. Requires the `benchbook` CLI: `go install github.com/seyallius/benchbook/cmd/benchbook@latest`. Never hand-edit a generated page — anything else under `docs/` starts with `<!-- generated by benchbook: DO NOT EDIT -->` and the next build overwrites it.

## Architecture

**Lifecycle (`lifecycle.go`)**: `Run(m, driver, schemaInit, dataInit, engineInit, opts...)` stores its state in a package global `runtime`, and `Reset` reads from that global. `resetMu` serializes resets so `t.Parallel()` tests can share one container. `Run` calls `os.Exit`, so tests drive the internals through `SetupForTesting`/`ResetForTesting` instead.

**Setup paths**:
- *Fast path*: the pristine dump file already exists, so setup calls `RestoreDump`.
- *Slow path*: setup runs `schemaInit`, then `dataInit`, then `GenerateDump` to write the pristine file.
- The engine is built after either path. `env.Engine()` is therefore **nil during `schemaInit`**, and `schemaInit` must open its own connection from `env.DSN()`.
- Snapshots persist on disk at `<testdataDir>/<driver>-pristine.sql` (default testdata dir: `<projectRoot>/testdata`, where the project root is found by walking up to `go.mod`). A stale dump survives schema changes. Use `WithGeneratePristine(true)` or delete the file to force the slow path.

**Reset strategies (`driver.go`)**:
- Each driver declares a `ResetStrategy`.
- `ResetStrategyRestoreDump` (MySQL, Postgres) restores the dump.
- `ResetStrategyTruncateAndSeed` (SQLite) calls `Truncate` and then re-runs `dataInit` on every reset. These drivers never generate or read a snapshot, even when a stale snapshot file exists, because it could corrupt the DB (Windows file locks, WAL races).
- Order of a reset: cache invalidator → `Engine.ClearCache()` → restore/truncate → seeders.

**Drivers**:
- `DatabaseDriver` is defined in the core package to avoid an import cycle. Each driver package (`drivers/{mysql,postgres,sqlite}`) imports core.
- `config.validate()` only accepts the three built-in `Driver` identifiers, so a custom driver must report one of them.
- MySQL embeds `mysql-quickstart-entrypoint.sh` (`go:embed`). That script hydrates a pre-baked empty data-dir tarball in `testdata` to skip initdb. If the tarball is missing, the driver auto-bakes one with a temporary container.
- MySQL and Postgres use testcontainers-go with tmpfs-backed containers.

**Configuration (`options.go`)**:
- The four required pieces are positional arguments to `Run`, so leaving one out is a compile error. Everything else is a `With...` functional option.
- There are deliberately no environment variables.
- `WithDriver`, `WithSchemaInitializer`, `WithDataInitializer` and `WithEngineInitializer` are deprecated but kept for backward compatibility. `Run` applies them internally.
- Options are last-write-wins, except `WithSeeders`, which accumulates.
- Driver-specific defaults (credentials, images) are set in `validate()`.

**Testing hooks (`testing.go`)**: this is a non-`_test` file, so `ApplyOptionsForTesting`, `SetupForTesting`, `ResetForTesting`, `NewEnvironmentForTesting` and `EnvWithEngineForTesting` are public API. Core tests live in the external package `snapdb_test/` and use a mock driver (`mock_driver_test.go`) that records calls.

## Conventions

- Each file starts with a `// Package <pkg>. <file>.go - <purpose>` header and uses banner section comments (`// ----- Types, Variables & Constants -----`, `Public API`, `Internal Helpers`, etc.). Follow both in new files.
- The core package must not import any ORM or the `testing` package (hence the `MinimalTandB` and `RunM` interfaces). ORM-specific code goes in adapter subpackages such as `xormadapter/`.
